## Кодекс поведения

Будьте уважительны к другим участникам. Оскорбления, токсичное поведение и дискриминация недопустимы.

## С чего начать

1. Сделайте форк репозитория на GitHub.
2. Склонируйте свой форк:
   ```bash
   git clone https://github.com/NightFox-YT/Realix.git
   cd <project-name>
   ```
3. Добавьте upstream-репозиторий, чтобы синхронизироваться с основной веткой:
   ```bash
   git remote add upstream https://github.com/NightFox-YT/Realix.git
   ```
4. Посмотрите список [issues](https://github.com/NightFox-YT/Realix/issues) — метка `help wanted` отлично подходит для первого вклада.

---

## Требования к окружению

Для сборки и отладки ОС потребуются:

- **Rust** (nightly toolchain, так как для bare-metal обычно нужны нестабильные фичи) + компонент `rust-src` + json-таргет i386-inknown-none
  ```bash
  rustup toolchain install nightly
  rustup component add rust-src --toolchain nightly
  rustup component add llvm-tools-preview --toolchain nightly
  ```
- **NASM** — ассемблер для 16-битного загрузчика
  ```bash
  # Debian/Ubuntu
  sudo apt install nasm
  ```
- **Make** — сборка проекта
- **QEMU** — для запуска и отладки образа ОС
  ```bash
  sudo apt install qemu-system-x86
  ```
- **GDB** — опционально, для отладки ядра через QEMU

---

## Сборка и запуск

```bash
make            # Собрать загрузчик, ядро и итоговый образ
make run        # Запустить образ в QEMU
make clean      # Очистить артефакты сборки
```

## Как вносить изменения

1. Создайте ветку от актуального `development`:
   ```bash
   git checkout development
   git pull upstream development
   git checkout -b feature/краткое-название
   ```
2. Вносите изменения небольшими логическими коммитами.
3. Убедитесь, что проект собирается и загружается в QEMU без ошибок и паник ядра.
4. Проверьте свой Rust-код (см. ниже).
5. Отправьте изменения в свой форк и откройте Pull Request в `development`.

## Стиль кода

### Rust (32-bit ядро)

- **`unsafe`-код** — сердце нашего ядра, но старайтесь инкапсулировать `unsafe` в безопасные обёртки, а не разбрасывать его по всему кодовой базе.
- Публичные функции и модули желательно снабжать doc-комментариями (`///`).

#### Стиль модуля

Каждый `.rs`-модуль оформляется единообразно (по духу — как asm-модули выше).

**Шапка модуля** (первые строки файла):
```rust
// © Realix > <Подсистема>: <Название>
// (ДД.ММ.ГГ) v<версия>
// ================
// ❗️ <Особые требования: инициализация, ограничения доступа и т.п.>
```
Версию и дату обновляйте только при существенных изменениях (изменение логики), не при перекладке кода.
За шапкой — блок импортов (`use`): сначала `core`/внешние, затем `crate::`.

**Doc-контракт `///`** — на каждой публичной функции и модуле, до кода:
```rust
/// <Что делает функция>
/// Параметры:
///  - <имя>: <что содержит>
/// Вывод:
///  - <что возвращает>
```

**Именование**: функции и переменные — `snake_case`; константы — `UPPER_CASE`; типы — `CamelCase` (стандарт Rust).

**Магические числа** (адреса, порты, флаги, лимиты) выносите в именованные `const` с поясняющим комментарием, а не оставляйте литералами в коде. Для порт-I/O предпочтительна форма через регистр (`in al, dx` / `out dx, ax`), тогда порт становится обычным `const`-операндом.

**Место хранения константы** — то же правило, что и для asm: значение, о котором должны договориться ≥2 модуля, — в общий модуль; используемое только одним модулем — локальный `const` в нём. Повышайте из локальной в общую лишь когда появился второй потребитель.

**Язык**: комментарии — на русском, сообщения пользователю — на английском.

### NASM (16-bit загрузчик)

- Используйте единый стиль отступов (4 пробела, без табуляций).
- Комментируйте нетривиальные операции с регистрами, сегментами — это сложно отлаживать без контекста.
- Магические числа (адреса, порты) выносите в константы через `%define` или `equ`.
- Не меняйте точку входа и лайаут загрузчика без обсуждения в issue — это ломает совместимость с BIOS/загрузкой.

#### Модель памяти и сегменты (для авторов модулей)

Модуль (`*.asm`, подключаемый через `%include`) наследует сегментное окружение той части, в которую его включают.
Чтобы модуль работал корректно, соблюдайте общую конвенцию:

- Считайте, что на входе в ваш код `ds` уже указывает на сегмент данных.
- Свои переменные (`db`/`dw`) объявляйте прямо в модуле.
- **Не полагайтесь на то, что `cs == ds`** (сейчас совпадают, но это может измениться).
  Никогда не адресуйте данные через `cs` и не ставьте `cs:`-префиксы «на всякий случай» — обращение к данным только через `ds` по умолчанию.
  Это то, что позволит в будущем разнести код и данные по отдельным сегментам (до ~128 КБ) без переписывания модулей.
- **Не меняйте `ds` внутри функций.**
  Если нужен доступ к чужому/физическому буферу - используйте `es` (или `fs`) и восстанавливайте его перед возвратом (`push es` / `pop es`).
- Входные указатели передавайте как смещение относительно `ds`, а не как «свободный `ds:si`».
- `DF = 0` - общий инвариант. Если модуль использует строковые операции, убедитесь, что направление прямое (`cld`).

#### Стиль модуля

Каждый `.asm`-модуль оформляется единообразно.

**Шапка модуля** (первые строки файла):
```asm
; © Realix > <Подсистема>: <Название>
; (ДД.ММ.ГГ) v<версия>
; ================
; ❗️ Зависимости: <модули/символы, которые требуются извне>
; ❗️ <Особые требования: инициализация и т.п.>
```
Версию и дату обновляйте только при существенных изменениях файла (изменение логики функций).

**Шапка функции** — контракт до кода:
```asm
; > <Что делает функция>
; Параметры:
;  - <регистр>: <что содержит>
; Вывод:
;  ! <какие регистры не сохраняются>
;  - <регистр/флаг>: <что возвращается>
```

**Данные — в конце файла**, не вперемешку с кодом. Рекомендуемый (не жёсткий) порядок: переменные → сообщения → таблицы.
Это упростит будущее разнесение кода и данных по секциям.

**Ошибки**: функции возвращают CF (0 — успех, 1 — ошибка) и `si` — смещение сообщения вида `'[!] EN: <текст>'`, где N — **сквозной системный номер ошибки** (единая нумерация `E1..EN` по всему проекту, не по модулям — чтобы один код искался по одной таблице).
Успешные сообщения начинаются с `'[+] '`. Фатальность решает вызывающий (`jc error_handler`), а не сама функция; фатальные сообщения, всегда ведущие в `error_handler`, номер не несут.

> **Bootix (`bootloader/bootix.asm`)** — исключение из общего правила: там **все** ошибки фатальны, так ещё и жёсткий бюджет 512 байт. Даже там, где по общей конвенции номер уместен, в Bootix его не добавляем — не пытайтесь туда «дописать» коды ошибок, это ломает сборку по размеру.

**Метки потока**: ошибочный выход — `.fail`, удачное завершение — `.done`, общий эпилог (снятие регистров + `ret`) — `.return`.
Отдельный `.return` нужен только там, где `.fail` и `.done` должны сойтись на одном эпилоге. Если такого разделения нет (ошибочная ветка просто печатает сообщение и проваливается в общий выход), `.done` совмещает удачное завершение и выход — плодить `.return` не нужно.
Флаги (`stc`/`clc`) выставляйте у самого выхода — между ними и `ret` не должно быть вызовов, портящих CF.

**Место хранения константы**: В `config.asm` — только то, о чём должны договориться ≥2 независимых модуля (общие адреса памяти, межстадийные контракты) и системные настройки. Внутри модуля — константы, используемые только им (или одной тесной семьёй команд). Совет: выноси в `config.asm` лишь когда значение понадобилось **второму** модулю; до этого держи локально, а при появлении общего потребителя — повышай из локальной в общую.

**Прочее**: локальные метки — `.snake_case`; константы — `UPPER_CASE` через `equ`/`%define`; магические числа выносить в константы; комментарии на русском, сообщения пользователю — на английском.

## Коммиты и сообщения

Используйте понятные сообщения коммитов, желательно в формате:

```
(<версия>) <область>: краткое описание

Более подробное объяснение при необходимости — что и почему
изменено, а не как (это видно из diff).
```

Примеры областей: `boot`, `kernel`, `drivers`, `build`, `docs`.

Пример:
```
(v0.14) kernel: fix double-free in page frame allocator
```

## Pull Request

- Заголовок PR должен кратко описывать суть изменения.
- В описании укажите:
  - что изменено и зачем;
  - как проверялось (запуск в QEMU, конкретные сценарии);
  - связанные issues (`Closes #123`).
- Будьте готовы вносить правки по замечаниям ревьюера — это нормальная часть процесса.
- Один PR — одно логическое изменение. Большие рефакторинги лучше обсуждать в issue заранее.

## Тестирование

Ручная проверка через QEMU — минимум: загрузка без паники, базовая работа проверяемой подсистемы.

---

## Отчёты об ошибках

При создании issue укажите:

- версию/коммит, на котором воспроизводится проблема;
- команду сборки/запуска;
- хост-систему (ОС, версия QEMU, версия Rust);
- лог паники ядра или вывод QEMU (по возможности — трейс);
- шаги воспроизведения.
